Perishable Markdown MVP · production integration

What gets logged every hour, and who has to produce it

Two parties, named consistently on this page: "you" is the engineering team integrating the pricing loop, and "the agent" is this codebase — the pricing service and its pipelines. The agent writes two event streams: a decision event when it sets a price, and an outcome event when that hour closes. The decision event needs nothing from you beyond the state you send to ask for a price. The outcome event is built by the agent from the hourly FLC feed (pipeline.ingest_outcomes), matched to decisions by SKU, FC, date and hour — so your whole integration is: call the API, apply the returned price, and tell the agent when a price push fails. Every field below carries a real example value, and §05 walks one episode end to end in payloads captured from the running system.

01The shape of it

One SKU in one fulfilment centre inside a clearance window is an episode. Every hour of that episode is a decision interval: the agent is asked for a price, it logs what it decided, you apply the price, the hour ends, and the agent reads the outcome back from the hourly feed.

Both streams are append-only JSONL with durable writes and duplicate detection. Nothing is ever silently dropped — an event that fails validation is written to a quarantine file with the reason attached, and the quarantine count is a monitored number.

You Price request 12 fields of state: what the item is, how much is left, how long it has, what price is in force now.
Agent Decision event 36 fields. The price it chose, everything it chose from, and every input it used — enough to re-solve the decision later.
You Price goes live The applied price must be the one the agent returned, or the mismatch rate climbs. A failed push is reported — that is the one outcome fact only you know.
Agent Outcome event Built from the hourly feed: units sold, inventory in and out, the price in force — matched to the decision by SKU, FC, date, hour.

Where the production table fits — and what stays yours

The interface on the outcome side is the hourly FLC production table you already maintain (sb_scm.fresh_flc_detail: inventory, units sold, discount, list price, cost, window counter per SKU × FC × hour). Hourly, keep your working state however you like — JSON, a temp table, anything; none of it is read. What matters is that once a day the table carries a row for every priced hour of the previous day — zero-sale hours included, which it does today — and pipeline.ingest_outcomes runs on it as a daily batch, builds the outcome events, and matches them to decisions. Daily is not a compromise: learning (pipeline.update) is itself a daily batch, so an hourly outcome stream would buy nothing.

The JSONL event streams described on this page are the agent's own storage — you never write or read JSON. Your two deliverables are both tables: the production table you already ship, and a small failed-pushes table (see §04). Going the other way, the agent dumps its decision and outcome logs as tables daily (pipeline.export_events — parquet, list fields JSON-encoded) for loading into the warehouse; those tables are a derived convenience for analytics and joins, never the audit record.

Why the decision event is so wide

It is an audit trail, not a log line. pipeline.assurance takes a logged decision, re-runs the solver from the event's own fields, and checks it gets the same price back. That is how a drifted model artifact or a bad config deploy is caught in production — but it only works if the event carries the full demand forecast (mu_ref_path) and the price already in force (anchor_discount), not just this hour's summary. None of those 37 fields is yours to produce.

episode_id: what it means, and how to assign it

An episode is one clearance window of one SKU at one FC: the run of consecutive selling hours from the hour the window opens until the listing closes. The id's job is to say "these hours are the same window", and the pricing logic leans on it through current_discount: prices may only hold or deepen within an episode, and a new episode is a fresh entry decision.

How to assign it:

  • Open a new id when a new window starts — the first hour a SKU × FC comes on clearance, recognisable in the source by the window counter resetting upward (a new flc_window value larger than the previous hour's would decrement to). Any scheme is fine as long as it is unique per window; ours is sku | fc | first hour of the window.
  • Keep that id for every subsequent hour of the window, however many calendar days it spans. Windows of 36 hours are common; midnight is an ordinary hour.
  • Never derive it from the calendar date. A date-keyed id splits one window into two at midnight. The second "episode" then starts with current_discount = null, the agent treats it as a fresh entry, and the price can move back UP mid-window — breaking the one guarantee (prices never rise within an episode) the system treats as structural. The horizon and the learning evidence for those hours are wrong too.
  • Two windows back-to-back are two ids, even with no gap between them: the close of one listing and the open of the next each carry their own entry decision.
  • A restock does NOT open a new id. Stock arriving mid-window — even one that extends the window, so hours_remaining jumps UP — is the same listing and keeps its id; just send the new, larger counter and the agent re-plans over the longer horizon. The id changes only when the listing actually closed and a new one opened. This is the case that matters: a new id here resets the price anchor, and the price could rise on shoppers who saw yesterday's — the one move the system guarantees never happens within a listing.

Consistency check worth building in: within one episode_id, hours_remaining should decrement by exactly one per elapsed hour, with one allowed exception — it may step UP on an hour where stock also arrived (a window-extending restock). Any other jump means the id is stitching two windows together or a feed hour is missing.

The agent refuses rather than returning an unsafe price

If the state is inconsistent — negative inventory, cost above list, a horizon that disagrees with itself, no feasible tier at or below the current price — the call raises StateRejected and no price comes back. Your integration needs a defined fallback for that path. It is deliberately not a silent default.

04The outcome event — built from your feed

You do not produce this event. pipeline.ingest_outcomes constructs exactly one finalized outcome per decision from the hourly FLC feed — the same snapshot the bootstrap already ingests — matched by (SKU, FC, date, hour). The fields are listed so you know what gets stored and what the feed must carry. The only per-hour fact that must come from you is a failed price push: one row per failed hour — a table (parquet/CSV) or JSONL, your choice — with sku_id, fc, date, hour_of_day, reason. No row means the push succeeded.

The inventory breaks, and what the ingester does with them

When a clearance window closes with stock still on hand, the source writes the remainder off and reports ending_inventory = 0 — about 13.5% of episodes end that way. The ingester classifies every non-reconciling hour itself, with the same rule the offline chain uses, so nothing here is yours to implement. For reference, given leftover = max(starting − sold, 0):

  • intraday_restock — ending > leftover. Stock was added mid-window.
  • episode_close_write_off — ending == 0 while leftover > 0.
  • unexplained_shortfall — 0 < ending < leftover. Shrink: units left the shelf that no sale or write-off accounts for. Named, not quarantined — the units stay visible through units_shrink and episode_scrap, and shrink runs at roughly 2.8% of decision hours, so leaving it unnamed fails the completeness gate for a reason no integration work can fix.

The write-off is recognised by the zero itself, never by position in the episode. Anything matching none of the three quarantines with the reason attached — the quarantine file is where a genuinely uninterpretable feed hour stays visible.

There is no exploration rate — plan for a lot of it

All three hours above explored, and that is not the seed being unlucky. The rule is simply: compute what every alternative price would cost in expected IL, keep the ones costing no more than tau_current, and if that set is non-empty, draw from it uniformly. There is no probability schedule, no base rate, no cap.

So a large share of priced hours will carry a price that is not the recommended one, and applied_price will differ from optimal_price on all of them. That is the product working, not a bug in the integration — but it is worth knowing before someone builds an alert on the divergence. The budget tau_current is what controls the volume, and it is recalibrated daily from realised spend.

The write-off shape

That last payload is why the classification exists: the source zeroes the field at close, so 2 − 1 = 1 expected against 0 reported. The ingester names it episode_close_write_off; unnamed, the store would quarantine it and event completeness would fall by the ~13.5% of episodes that end holding stock.

Note also that is_stockout is false on all three, including the write-off. Stockout means the shelf emptied — the hour reconciles with starting − sold == 0 — so neither a write-off (stock remained) nor a restocked hour that sold past its opening count (the shelf never sat empty) is one.

06The thresholds these feed

Event quality is gated, and two of these gates can suspend the system. Worth knowing before you scope, because they set the reliability bar on the outcome stream.

Exactly-once, on the agent's side

Outcome ids derive from decision ids, so re-running the ingester over the same feed dedups instead of double-counting, and learning consumes each outcome_id once. Nothing on your side needs exactly-once delivery — the feed just needs to keep carrying every hour.

07The parts worth checking first

Ranked by how much trouble they have caused in replay and shadow. If your team can answer these five, the rest of the contract is routine field plumbing.

  1. hard Is episode_id stable across midnight?

    The full assignment rule is in the box under §02. Thirty-six-hour windows are common; a date-derived key splits one window into two, resets the price anchor mid-window (the price can then rise — the one guarantee the system treats as structural), and makes every horizon in the second half wrong.

  2. hard Does hours_remaining mean hours, reliably?

    It has to equal the number of hours actually left in the window, this one included. The service plans over exactly that many hours and rejects the state if its forecast path and your counter disagree. Upstream data has historically carried very large values here from defects; anything above 120 hours is treated as bad data, not a long window.

  3. medium Does the hourly feed keep carrying every priced hour — zero-sale hours included?

    Outcomes are built from the feed, so a priced hour the feed drops is a completeness miss. Roughly three quarters of hours sell nothing, and those rows are the evidence — the feed carries them today; it must keep doing so for the pilot SKUs.

  4. medium Can you report a failed price push?

    The one outcome fact only you know. One table row per failed hour (sku_id, fc, date, hour_of_day, reason); silence means the push succeeded. The feed's own discount column backstops this — a price that never went live shows up as a mismatch — but the explicit report is what separates "push failed" from "feed skew".

  5. medium Are cost and original_price available per hour, per FC?

    Cost sets the price floor, so a stale or missing cost either blocks legal discounts or permits below-cost ones. Both are per-request inputs, not reference data the agent holds.

Field lists are read directly from the running system — events/store.py (DECISION_REQUIRED, OUTCOME_REQUIRED), inference/decide.py for what the agent emits, pipeline/ingest_outcomes.py for how outcomes are built from the feed, and config.yaml for every threshold quoted in §06.

Every payload in §05 was generated by running the real decision path against the frozen artifacts and capturing what it emitted — including the write-off, classified by the same adjustment_reason function the ingester runs. The long unrounded floats are shown as they arrive, not tidied.
