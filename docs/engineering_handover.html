Lane B handoff — the process, the scripts, the contract

One page for the engineering team, written so the pilot can be run with the least possible back-and-forth. The principle: we wrote the scripts; you supply the data you already produce, apply the price we return, and run two cron jobs. Nothing here asks you to build a request or compute a feature — those are derived by our code from the hourly table you deliver today. One thing in the data is yours: the episode_id that names a clearance window. You own the data, and in time the whole pipeline, so you assign it; the rule is written down and shipped as a script you can run as-is or port (0.2). The phases below are in the order they happen; every task says what you do, the command, what it produces, what to check, and what to send or do next. The contract that used to be a separate page is the appendix, for reading a decision when you need to. For the integration phase you run the pricing folder, whose stateless contract is section 10; where it differs from the phases above, section 10 wins.

01The loop, and who does what in it

The engine is a black box to you, and for the integration phase it is a folder (section 10). Every hour it is handed the shelf as it stands and returns a price per item, from the row alone: nothing is remembered between hours. Every morning it pulls the trailing days of the hourly table from the warehouse and writes the day's feature table. Learning happens elsewhere: the owner's lane in the repository reads the log the folder writes and the feed the warehouse holds, and what it learns comes back as new files in artifacts/. 0.2a · Assign the episode id

The id says "these hours are the same clearance window". It is the one column in the snapshot that is not already in your feed, and it is yours: you know whether a listing was extended or relisted, and the pipeline will be yours to run. The rule is the one our offline chain applies to your history, stated for one clock hour so it needs nothing but this hour's rows and last hour's:

A shelf's row continues last hour's episode on that shelf when all three hold: last hour's row is exactly one hour earlier; it did not close the shelf (ending_inventory is not the write-off zero); and the counter stepped down by one, or stepped up or stayed flat while stock arrived (ending_inventory > inventory − units_sold last hour). Otherwise the row opens a new episode named skuseq|fc|<date>T<hour>. Any unique name works for a new window; that one is ours.

You doEither run our script on each hour's rows before writing the snapshot, or port the rule into the job that writes it. Either way the ids must come out the same as the rule's, because the engine checks every hour and counts the disagreements.
Commandpython3 -m ops.assign_episode_ids --hour <this hour's rows> --previous <last hour's rows, with their ids> --out snapshots/<date>T<hh>.parquet. The first hour ever has no --previous and opens every shelf.
ProducesThe same rows with one column added, episode_id, and a line of counts: continued, new, rows naming no shelf-hour.
CheckAfter the first hour, most shelves continue; a new id appears when a listing opens or the write-off zero closed the shelf. Within one id the counter steps down by one an hour, stepping up only on the hour after stock arrived.
ThenIf you port it, run both on the same two hours and diff the ids; send us the diff (empty) and the counts.

Carry the same id into the nightly feed as well, on every row. You have already computed it for the snapshot, so it costs one column. It earns two things. A clearance window becomes a plain group-by for everyone downstream, rather than something each reader re-derives from counter steps. And it lets ops.check_inputs --feed read a whole day of your ids against the rule at once, which is a far stronger check than the hour-by-hour count the pricing script can do. The check compares the window boundaries, never the id's spelling: your scheme is yours, and two ids agree when they group the same rows.

The folder's hour is stateless: it prices each row from the row, the artifacts and the feature table of the row's episode's opening day, reads no store, and appends its decisions and refusals to events_store/ as a log it never reads. Two fields of your row carry what the repository's hour takes from its store: episode_id is the opening tag <skuseq>|<fc>|<day>T<hh> (0.2a spells it so), and a row whose tag is its own shelf-hour is the episode's first hour; discount is null on that first row and, on every later row of the episode, the discount the service applied last hour, piped back by you — the anchor. A later row without it is refused, never priced as an entry; an id that is not a tag, names another shelf or opens after the row's hour is refused with the reason and counted (episode_ids_that_place_no_hour). The rule check (0.2a's disagreement count) runs in the repository's morning lane, not on the host. flock -n skips a run that would overlap the previous one instead of stacking it; the event store also locks itself on every write, so an overlap that does slip through is refused rather than double-priced.
Time zone and daylight savingdate and hour mean the feed's own wall clock, whatever zone your feed is written in. The morning lane takes the trading day from the feed file it is given, never from the host clock, and the feature table is dated the day after that feed. At a daylight-saving change the feed's clock repeats or skips an hour: a repeated hour is two rows for one shelf-hour and both are refused (the outcome matches neither); a skipped hour reads as a missing snapshot hour for that shelf. Tell us the dates in advance.

04Phase 2 · Every clock hour

Four steps, one command. The cron does the first three; the fourth is a table you append to during the day.

What the script does with the snapshot, so its output makes sense: it keys every row on (skuseq, fc, date, hour) and reads your episode_id as given. An id the store has never priced on that shelf is an entry decision; the id the store last priced on that shelf continues the episode, anchored on the discount your snapshot says is on the shelf, so a push that failed last hour is priced from the price shoppers actually see. It also evaluates the rule of 0.2a itself — against the closed rows when you send them, else against its last decision on the shelf — and counts the ids that disagree with it; it never overrides yours. It reads the day's feature table, prices, commits every decision to the event store, and writes the response.

08Rules, and who owns what

  • Reload the posterior once per batch if you lift the engine into a long-lived service (PosteriorStore.reload() before pricing). The monitor writes suspensions and --apply writes updates into the same file from other processes; a handle that never reloads keeps exploring on a suspended pilot. ops.price_batch does this for you.
  • The exploration budget comes from the store (PosteriorStore.tau), never from exploration.tau_initial in config, which is only the launch value.
  • Never run daily.update --apply. It is the operator's gate.
  • Safety is structural, not configured on your side: the cost floor and the never-rises-within-a-window rule live in the engine's action set. There is nothing for the caller to check or enforce.
  • The bundle is sealed. Do not edit artifacts/ or config.yaml; a moved file shows as a red seal row in ops.status and the lane stops.

10The pricing folder — the stateless contract, for the integration phase

For the integration phase you run the pricing folder (integration/), not the repository: three commands, the artifacts and the config the owner copies in, and the directories below, nothing else. Its hourly service is stateless. Every row is priced from the row itself, the model files and the feature table of the row's episode's opening day; nothing is looked up from an earlier hour, no store is read, and a re-sent hour gets the identical answer. Everything the repository's hour took from its store, your row now carries. The phases above still describe the loop; this section is the contract where the folder differs, and it wins where the two disagree.

episode_id: what it means, and how to assign it

An episode is one clearance window of one SKU at one FC: the run of consecutive selling hours from the hour the window opens until the listing closes. The id's job is to say "these hours are the same window", and the pricing logic leans on it through current_discount: prices may only hold or deepen within an episode, and a new episode is a fresh entry decision.

How to assign it (the exact rule, and the script that applies it, is task 0.2a; what follows is the same rule in words):

  • Open a new id when a new window starts — the first hour a SKU × FC comes on clearance, recognisable in the source by the window counter resetting upward (a new flc_window value larger than the previous hour's would decrement to). Any scheme is fine as long as it is unique per window; ours is sku | fc | first hour of the window.
  • Keep that id for every subsequent hour of the window, however many calendar days it spans. Windows of 36 hours are common; midnight is an ordinary hour.
  • Never derive it from the calendar date. A date-keyed id splits one window into two at midnight. The second "episode" then starts with current_discount = null, the agent treats it as a fresh entry, and the price can move back UP mid-window — breaking the one guarantee (prices never rise within an episode) the system treats as structural. The horizon and the learning evidence for those hours are wrong too.
  • Two windows back-to-back are two ids, even with no gap between them: the close of one listing and the open of the next each carry their own entry decision.
  • A restock does NOT open a new id. Stock arriving mid-window — even one that extends the window, so hours_remaining jumps UP — is the same listing and keeps its id; just send the new, larger counter and the agent re-plans over the longer horizon. The id changes only when the listing actually closed and a new one opened. This is the case that matters: a new id here resets the price anchor, and the price could rise on shoppers who saw yesterday's — the one move the system guarantees never happens within a listing.

Consistency check worth building in: within one episode_id, hours_remaining should decrement by exactly one per elapsed hour, with one allowed exception — it may step UP on the hour after stock arrived (a window-extending restock; the restocked hour itself still counts down). Any other jump means the id is stitching two windows together or a feed hour is missing.

E·05The outcome event — built from your feed

You do not produce this event. daily.ingest_outcomes constructs exactly one finalized outcome per decision from the hourly FLC feed — the same snapshot the bootstrap already ingests — matched by (SKU, FC, date, hour). The fields are listed so you know what gets stored and what the feed must carry. The only per-hour fact that must come from you is a failed price push: one row per failed hour — a table (parquet/CSV) or JSONL, your choice — with sku_id, fc, date, hour_of_day, reason. No row means the push succeeded. A failed-push row that matches no decision is counted (push_failures_unmatched in the ingest report) rather than dropped silently — a non-zero count means your table and the agent's decisions disagree on the hour key; a row naming no hour at all (a null id, a blank line) costs itself, counted as push_failures_unkeyable, never the batch. The table may use the feed's own column names (skuseq, hour). An empty feed is a whole day of gaps (feed_empty), never a day outside the feed.

The inventory breaks, and what the ingester does with them

When a clearance window closes with stock still on hand, the source writes the remainder off and reports ending_inventory = 0 — about 13.5% of episodes end that way. The ingester classifies every non-reconciling hour itself, with the same rule the offline chain uses, so nothing here is yours to implement. For reference, given leftover = max(starting − sold, 0):

  • intraday_restock — ending > leftover. Stock was added mid-window.
  • episode_close_write_off — ending == 0 while leftover > 0.
  • unexplained_shortfall — 0 < ending < leftover. Shrink: units left the shelf that no sale or write-off accounts for. Named, not quarantined — the units stay visible through units_shrink and episode_scrap, and shrink runs at roughly 2.8% of decision hours, so leaving it unnamed fails the completeness gate for a reason no integration work can fix.

The write-off is recognised by the zero itself, never by position in the episode. Anything matching none of the three quarantines with the reason attached — the quarantine file is where a genuinely uninterpretable feed hour stays visible.

There is no exploration rate — plan for a lot of it

All three hours above explored, and that is not the seed being unlucky. The rule is simply: compute what every alternative price would cost in expected IL, keep the ones costing no more than tau_current, and if that set is non-empty, draw from it uniformly. There is no probability schedule, no base rate, no cap.

So a large share of priced hours will carry a price that is not the recommended one, and applied_price will differ from optimal_price on all of them. That is the product working, not a bug in the integration — but it is worth knowing before someone builds an alert on the divergence. The budget tau_current is what controls the volume, and it is recalibrated daily from realised spend.

Exactly-once, on the agent's side

Outcome ids are the hour's key (feed-<sku>|<fc>|<date>T<hh>), so re-running the ingester over the same feed dedups instead of double-counting, and learning consumes each outcome_id once; a price batch re-sent for an hour already priced is refused before it reaches the store. Nothing on your side needs exactly-once delivery — the feed just needs to keep carrying every hour.

H·08The parts worth checking first

Ranked by how much trouble they have caused in replay and shadow. If your team can answer these five, the rest of the contract is routine field plumbing. Separate from feasibility, §01 lists the meanings the agent has assumed about your table — those need your sign-off, not your engineering time.

  1. med Have you watched one cycle run end to end?

    python3 -m tools.e2e_cycle (§03) prices hourly request batches through ops.price_batch, sells them in a simulated shop, writes the feed, ingests the outcomes and exports the paired tables, all under sim/e2e. The files it writes are the files you will produce and read; a question about a field is faster asked of them.

  2. hard Is episode_id stable across midnight?

    You assign the id, by the rule in task 0.2a (ops.assign_episode_ids applies it; the same rule in words is the box under §03). Thirty-six-hour windows are common; a date-derived key splits one window into two, resets the price anchor mid-window (the price can then rise — the one guarantee the system treats as structural), and makes every horizon in the second half wrong.

  3. hard Does hours_remaining mean hours, reliably?

    It has to equal the number of hours actually left in the window, this one included. The service plans over exactly that many hours and rejects the state if its forecast path and your counter disagree. Upstream data has historically carried very large values here from defects; anything above 120 hours is treated as bad data, not a long window.

  4. medium Does the hourly feed keep carrying every priced hour — zero-sale hours included?

    Outcomes are built from the feed, so a priced hour the feed drops is a completeness miss. Roughly three quarters of hours sell nothing, and those rows are the evidence — the feed carries them today; it must keep doing so for the pilot SKUs.

  5. medium Can you report a failed price push?

    The one outcome fact only you know. One table row per failed hour (sku_id, fc, date, hour_of_day, reason); silence means the push succeeded. The feed's own discount column backstops this — a price that never went live shows up as a mismatch — but the explicit report is what separates "push failed" from "feed skew".

  6. medium Are cost and original_price available per hour, per FC?

    Cost sets the price floor, so a stale or missing cost either blocks legal discounts or permits below-cost ones. Both are per-request inputs, not reference data the agent holds.

2. Apply the returned price

applied_price is what goes on the shelf, exactly that number. The engine matches its decision against the price your feed shows in force; the mismatch rate is gated (contract §07) and a breach suspends exploration. A price you could not apply is a failed push (next item), never a silent mismatch.

3. Report failed price pushes

The one outcome fact only you know. One row per failed hour, as a table (parquet or CSV) or JSONL:

skuseq, fc, date, hour, reason      # or sku_id, fc, date, hour_of_day, reason: either spelling is read

No row means the push succeeded. Keys are normalised on read the same way requests are. A reported failure is counted apart (push_failures_applied in the ingest report) and excluded from learning; an unreported one is caught by the mismatch gate as if it were your bug.

4. A fallback for a rejected request

When a row comes back rejected, hold the current shelf price and alert on the rejection rate. Do not retry the same hour with altered fields to get a price out; the next hour's request is the retry.

5. The daily cron

Once per day, after the previous day's hourly feed has landed (the "every morning" column of §03):

python3 -m ops.advance --feed <yesterday's hourly FLC parquet> --failures <yesterday's failed pushes>

Omit --failures on a day with none. One command runs the lane in order: ingest outcomes (from the feed, matched to decisions on sku_id, fc, date, hour_of_day), walk the exploration budget, monitor (guardrails and stop conditions), assurance, export the paired tables, status. It stops at daily.update --apply, the operator's gate, and never runs it. It keeps running the lane while status is red; a red stop names the row and what clears it.

Field lists are read directly from the running system — events/contract.py (DECISION_REQUIRED, OUTCOME_REQUIRED, REJECTION_REQUIRED; events/store.py enforces them), engine/decide.py for what the agent emits, daily/ingest_outcomes.py for how outcomes are built from the feed, and config.yaml for every threshold quoted in Appendix G.

Every payload in §06 was generated by running the real decision path against the frozen artifacts and capturing what it emitted — including the write-off, classified by the same adjustment_reason function the ingester runs. The long unrounded floats are shown as they arrive, not tidied.
