The rehearsal that uses the real world

The previous tab replayed history through our own model of it. This one runs the complete production decision path against live data while the legacy rule keeps pricing: real inventory, real windows, the real price already in force constraining what the agent may do next, every decision logged through the same event store production will use — and not one won of it applied to a shelf.

Three rungs, and only one of them is about value

These three sit in a strict order, and the most common mistake in this whole project would be to read a number from one rung as if it answered the next one's question.

Run on a window nothing was fitted to

Every artifact in this system stops at the end of the test window. The stretch after it is a hold-out: no model was trained on it, no factor was fit to it, no gate was decided on it, and nobody has looked at it. Standing at the end of the test window and walking that stretch forward is the only unrehearsed test the data can give.

It matters because most of the checks in this document grade something that was fitted to the window it is graded on. The clearest case is the exploration budget: the replay solves for a threshold until spend equals budget, so it reports a perfect match on any population it is handed — including one where the answer is wrong by a factor of eight. A number a procedure solves for is not evidence about that number.

It is a one-shot resource. Tune a value on it and re-run, and it has quietly become a second calibration set. Which is why the readings below are written down before the run rather than after it.

And it is the default, not an option. The honest run being the one someone has to remember to ask for is how in-sample numbers end up on a launch decision. Running on the full history instead is still possible, and the report then carries a caveat naming exactly which figures that flatters — the drift ratio, the threshold derivation and the learning yield — and which it leaves untouched, because the three gate checks test plumbing rather than fit.

Is the frozen model still describing reality?

The demand model is frozen at launch and never retrained during the MVP. That is a bet, and this is the only place it gets tested before real money rides on it: the hold-out sits weeks past the end of the training window, so the drift ratio measured here is the frozen model grading itself on data from after its own world ended.

realised sales ÷ predicted sales, at the price that was actually charged — 1.00 the model still describes the world >1.00 demand has risen, or the level was always under-called <1.00 the model is now optimistic — and the agent prices on its optimism

This is the production continuation of the calibration gate, not a substitute for it: the gate asks whether the model is usable at all, on a window chosen in advance; this asks whether it has stopped being usable since. The same ratio runs daily once the pilot is live, which is what makes a frozen model defensible rather than merely convenient.

Does the pilot survive its own first day?

Exploration is a budgeted line item: at most 1% of markdown loss — measured as the trailing 7-day average of the IL of episodes that closed each day, so the day's budget is fully knowable at midnight — spent on deliberately non-optimal prices in exchange for evidence about price response. The threshold τ controls how much gets bought, it corrects itself daily against realised spend, and above 2× budget a stop condition suspends exploration outright.

The correction reads only yesterday — so the launch value has to be right

τ adjusts by comparing yesterday's spend to yesterday's budget, clipped asymmetrically — it can halve in a day (cutting is the safety direction) but rise at most 25% (raising is never urgent). On day one there is no yesterday. So the first day is spent at whatever τ the system launched with, the stop condition is evaluated on that day's spend, and a τ that is badly too generous suspends exploration before the first correction exists. The learning loop would then never start, and nothing in the daily monitoring would look broken — exploration would simply be off.

So the shadow run re-derives τ on the decision path production actually walks, and then simulates the controller day by day across the hold-out. The reading is fixed in advance:

And what would it have learned?

Every exploration decision buys a measurable quantity of evidence about price response. Shadow adds it up and converts it into the only unit that matters to a plan: how many episodes it takes to move the belief by one bounded step.

  • Episodes per bounded update—
  • Belief moves at most0.15 per update
  • Updates per day1 — human gate

Two floors sit under the learning rate and the larger one binds. The evidence floor is how long it takes to accumulate enough observations for a step. The calendar floor is fixed no matter how much evidence arrives: the belief may move at most 0.15 per update and at most one update commits per day, so shifting it by 0.6 takes four days minimum even with infinite data. At production volume the calendar floor is expected to be the binding one — which is worth knowing, because it means throwing more episodes at the problem does not speed it up.

What shadow still cannot tell us

The recommendations were never applied, so every outcome recorded here happened under the legacy price. They are marked ineligible for learning in the event store and the update pipeline refuses to consume them — a recommendation the world never saw is not evidence about that recommendation, and the code enforces that rather than trusting anyone to remember it.

So: no inventory-loss figure, no clearance comparison, no scrap comparison. Shadow proves the machine runs correctly against reality and shows how far its advice diverges from today's. The A/B remains the only thing that can say whether the advice is better, and it is designed on the assumption that the replay tab's number might not survive contact with the world.
